# Life Agent Factory Method

Life Agent Factory is a method for designing personal agents from recurring life loops. A life loop is any repeated cycle of desire, action, record, interpretation, adjustment, and return.

The method is useful when the user says something like "I want to improve cooking," "I want to reflect on dancing practice," or "I need help thinking through research." These are not yet agent specs. They are invitations to discover what should be noticed, remembered, questioned, and repeated.

## Method Stages

1. Intake normalization: translate the user's vague desire into a working life area without narrowing too early.
2. Life scan: find recurring moments where the user already acts, avoids, records, forgets, compares, or reflects.
3. Domain diagnosis: identify the kind of life work involved.
4. Loop extraction: name the smallest repeatable loop worth supporting.
5. Memory contract: define what is captured, how it is summarized, and what requires consent.
6. Role decomposition: divide the agent into clear behaviors rather than one vague helper.
7. Ritual design: create a recurring interaction with triggers, prompts, outputs, and cadence.
8. MVP compression: remove everything not needed for the first useful loop.
9. Blueprint writing: produce a structured Agent Blueprint.
10. Review and revision: evaluate for usefulness, respect, specificity, and repeatability.
11. Evolution (user-triggered): when the user later runs the evolve flow, re-run the review discipline against the existing blueprint plus the user's lived evidence, and converge the blueprint by one minor version step.

## Design Question

The factory's central question is:

What life loop is broken, worth recording, worth improving, or worth reflecting on?

Everything else follows from that.

## Evolution (User-Triggered)

The first ten stages build an agent. Stage eleven maintains it. Evolution is not a separate machine; it is the review stage (stage ten) re-run against an agent the user has actually lived with, plus the evidence they bring back. It is user-triggered only — the factory never initiates, schedules, or hints that a revision is due.

Each evolution produces one minor version step (vX.X -> vX.X+0.1) on the same loop: re-voicing, memory tightening, ritual de-frictioning, boundary sharpening, and at most one paid-for addition, applied only with the user's per-change approval. A change to the loop's own identity is not an evolution — it is a new agent built from stage one.

## Directional Invariant

Evolution has a right direction, and it is not "more." A revision must leave the blueprint a more faithful fit to the loop the user has actually lived AND no heavier to run on a low-energy day. Fit may rise; felt load never does. Surface shrinks by default and grows only against a high, paid-for bar.

This holds across every domain because every domain fails the same two ways — the ritual costs more than the user has on a bad day, or the agent oversteps and loses trust — and both are cured by removing or sharpening surface, not adding it.
